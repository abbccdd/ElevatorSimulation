# 多电梯群控算法组会演示指南

## 演示目标

这个入口用于 UI 尚未完成时展示已合入 main 的正式核心。`Demo/AlgorithmDemo.cpp` 不实现第二套算法，只构造固定输入，调用 `ElevatorDispatcher`、`Elevator`、`Simulation` 的公开接口并打印只读快照。所有场景固定、可重复，适合现场讲解和录屏。

建议用 8~10 分钟完成。主线不是逐行讲代码，而是回答三个问题：为什么选这台梯、状态变化后为什么会改派、容量暂时不足时为什么不会阻塞其他请求。

## 演示前准备

最方便的方式是直接双击项目根目录的 `启动算法演示.bat`。首次运行或 Core/Demo 源码变化时，启动器会自动编译 x64 版本；源码内容未变化时直接复用已验证的缓存程序，然后进入逐场暂停模式。哈希检查失败会安全回退到重新编译，不会运行无法确认版本的旧程序。演示结束或发生错误后窗口会保留。

在项目根目录打开 PowerShell，运行：

```powershell
& '.\Demo\RunAlgorithmDemo.cmd' x64 --all
```

确认六个场景全部结束且返回码为 0。正式组会建议使用逐场暂停模式：

```powershell
& '.\Demo\RunAlgorithmDemo.cmd' x64 --step
```

每讲完一页按回车进入下一场景。也可以只运行一个场景，例如：

```powershell
& '.\Demo\RunAlgorithmDemo.cmd' x64 3
```

第二个参数 `1..6` 对应六个场景。脚本使用现有 Visual Studio/MSVC，以 C++17、`/W4 /WX`、`/utf-8` 编译，并按源码内容 SHA-256 自动失效缓存；产物仅写到被忽略的 `build/algorithm-demo/x64/`。没有新增 VS 工程、库或安装步骤。中文乱码时不要直接双击 exe，使用脚本让控制台切换到 UTF-8。

## 建议讲解顺序

### 开场，约 40 秒

建议这样说：

> 队友负责的动态界面还在开发，所以我做了一个只读控制台入口。它不复制业务算法，直接链接正式 Core。今天展示的是同一套 Dispatcher、Elevator 和 Simulation 在固定场景下的真实输出。

指出三层边界：Dispatcher 只读评分，Elevator 执行已接受任务，Simulation 唯一拥有乘客并统一推进时间。

### 场景 1：ETA 与容量路线预演，约 1 分钟

观察三台候选的 ETA、Cost 和请求层预计载客量。

- E1 是远处同向顺路梯。
- E2 已在 10F，因此应立即响应，说明“顺路”不会绝对压过空闲梯。
- E3 当前满载，但 8F 有已知下客，因此预测到 10F 已有空位，仍是可行候选。

一句话总结：评分依据事件级 LOOK 路线和预计容量，而不是固定优先级或“当前满载就永久排除”。

### 场景 2：Aging，约 1 分钟

先看新请求，再看等待 200 秒后的同一请求。强调公式：

```text
AdjustedCost = ETA + LoadCost + max(0, DirectionCost - AgingBonus)
AgingBonus = min(8, waitingSeconds × 0.05)
```

Aging 有上限，只抵消有限方向成本，不会掩盖真实路线时间。输出中选梯变化说明旧请求的竞争力会逐步提升。

### 场景 3：有限联合分配，约 1.5 分钟

这是最适合重点展示的反例：E1 在 5F、E2 在 1F，请求依次为 4F 上行和 6F 上行。

- 逐个贪心得到总 Cost 12。
- 两请求联合规划得到总 Cost 8。
- 程序同时打印叶组合数和评分次数。

强调搜索有明确上限：每批最多三个 Active 请求、每层最多三台候选加“不分配”分支，最多 64 个叶组合。结论是这个固定反例更好，不声称全局最优。

### 场景 4：动态改派，约 1.5 分钟

先展示 15F 上行请求的原负责梯，再加入 17F 下行请求。新任务改变路线后，15F 请求从 E2 改派到 E3。

强调改派是事件触发的，并同步三件事：旧梯撤销外呼、新梯添加外呼、Simulation 更新唯一归属。为防止来回抢单，仍有 5 秒收益阈值、10 秒冷却、真正接近一层保护和正在服务锁。

### 场景 5：DeferredCapacity，约 1.5 分钟

三台梯先全部满载上行：12~14F 的上行请求当前不可行，因此显示为“未分配/Deferred”。随后加入 15~17F 下行请求：

- 前三个 Deferred 保留在真实 FIFO 中，首次请求时间不重置。
- 后三个 Active 不被阻塞，直接参加联合分配。
- 路线顺序变化后的事件会重新调用同一 `ScoreSnapshot`，Deferred 自动恢复。

说明 DeferredCapacity 是核心语义，控制台文字不是新增永久状态；未来 UI 可以把它显示为灰色“等待运力”。

### 场景 6：端到端仿真，约 1 分钟

最后用固定 seed 注入 90 名乘客并一次运行到结束。指出送达、等待、乘梯中、平均等待、最大等待和平均乘梯时间。`ValidateState()` 同时验证 Floor 队列、Elevator ID、活动 Passenger 和 Statistics 人数守恒。

### 收尾，约 30 秒

建议这样说：

> 当前成果完成了可测试的群控核心：LOOK 事件级 ETA、容量和 FIFO 目标层预测、Aging、有限联合分配、带滞回改派及 Deferred。它不依赖 UI，也没有使用 AI 或复杂预测。现阶段边界是有限搜索不保证全局最优，持续超载也没有严格等待上界。

## 现场常见问题

**为什么不用未完成的 MFC 界面？**  控制台入口隔离了展示风险，并证明 Core 与 UI 解耦；后续 UI 只需调用相同公开接口和快照。

**这些输出是不是手写的？**  标题和解释文字是演示层，ETA、Cost、选梯、归属、统计和一致性结果全部来自正式核心。

**为什么 Aging 不直接减 ETA？**  ETA 表示物理接客时间。Aging 调整竞争成本且有 8 秒上限，避免为了旧请求无条件选择极差路线。

**联合分配是不是全局最优？**  不是。它只联合最老三个 Active 请求并截断候选，目标是在课程设计可解释性和计算开销之间取得平衡。

**Deferred 会不会饿死？**  它保留原请求时间，Aging 连续；容量释放和路线变化事件会重评估。但在长期超过系统运力时，任何调度算法都无法给出有限等待保证。

**如何证明不是 UI 帧率影响结果？**  调度只在模型事件置脏时运行；固定 seed 和分帧一致性测试验证不同 Update 分片得到同一状态。

- 关闭会遮挡终端的通知，终端字号建议 18~22。
- 提前运行一次 `x64 --all`，再用 `x64 --step` 演练讲解节奏。
- 正式展示可以直接双击根目录的 `启动算法演示.bat`。
- 准备一张备用截图或录屏，以防现场投影环境无法运行 VS 工具链。
- 不把历史性能对照说成全局改进；同时说明送达量、积压和完成样本口径。
